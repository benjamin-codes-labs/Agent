# Project verification

- Use `.venv/bin/python -m pytest -q` for the full test suite. The project virtual environment includes the scientific imaging dependencies required by `tests/test_get4.py`; the system Python may not.
- The supplied TIFFs use LZW compression; `imagecodecs` is required to decode them and is listed in `requirements.txt`.
- Tests must remain offline. `tests/conftest.py` blocks accidental real Anthropic client construction.
- GET4 batch grouping uses `Batch_*` folders as battery types, not the battery name in `img_batteryname_filter` filenames. BSE, ETD and Inlens are analysed separately.
- Running `.venv/bin/python sentinel/GET4.py` without arguments analyses the project-relative `Batches` directory and writes only `all_batch_comparisons.json` in the project root. It does not depend on the shell's working directory for input/output defaults. SE images are excluded and recorded in `excluded_images`.
- GET4 uses placeholder intensity segmentation. Detector-specific material phase identities are not validated, and pairwise batch comparisons do not establish independently replicated battery-type effects.
- `KnowledgePack.from_project(root)` loads `SiC_SEM_reference_verified.json` and `all_batch_comparisons.json`, preserves verification/caveat metadata, excludes deleted reference entries, and provides source-linked `context.*` facts. Do not map Batch_1/2/3 to A/B/C or equate GET4 intensity classes with another pipeline's material segmentation.
- `main.py` defaults to `examples/facts.json`, the supplied native pipeline JSON, not the deleted BAT example files. Never rewrite, wrap, rename fields in, or normalise values in that input. `--facts path.json` selects another document; `--sample` is an alias. A single record, a list, a samples/results/images collection, or a sample-keyed mapping is read without changing the file. All records are sent together in one generation request per attempt, followed by one whole-document critic pass, not per-image model calls.
- Facts-file output is a JSON object mapping each `sample_id` to ONE string: its reasoning points, each as a `- ` bullet on its own line (`main.POINT_PREFIX`, `main.POINT_SEPARATOR`), in input order. There is no heading: the key identifies the image and the website shows the category and probabilities. `format_facts_response` in `main.py` builds it and `main()` returns the same dict. Missing/extra/duplicate sample results, changed decisions, cross-sample fact or citation references, and partial/truncated results are rejected.
- `main.py --question "..."` without a facts file remains general knowledge Q&A. Explicit `--image` previews are available only in that mode. Facts-file narration is text-only: image paths are provenance, not attachments. `--debug` and progress go to stderr; stdout contains only the result.
- `main.py` loads `.env` relative to the project root and requires AI-generated output: it sets `WorkflowConfig(allow_template_fallback=False)` and reports generation, validation or critic failures instead of displaying a template. Legacy/offline callers can still allow the template through the workflow configuration. Missing `ANTHROPIC_API_KEY` prevents generation; changing prompts does not fix authentication.
- Facts-file explanations target 100-150 reasoning words per sample. A shared per-image budget reserves the exact heading length and enforces a 280-word total ceiling, allowing a small margin over the preferred 250-word summary. The generation manifest includes the heading and exact target/maximum reasoning budgets. Counts use rendered text after placeholder substitution; overlong repairs target at most 120 reasoning words, not a minimal trim. There are up to five reasoning points. They include the basis, why alternatives fit less well (or cannot be excluded), and material limitations. Refusals/known-location routes are explained as such, not converted into new-material classification claims. General Q&A retains its 280-word/six-point limits. Overlong drafts are repaired, not truncated; citation metadata is not displayed.
- `sentinel/pipeline_facts.py` embeds field semantics adapted from the supplied markdown and inspected pipeline definitions, never its illustrative measurements. `decision.answer` wins when present; otherwise use `predicted_batch`. Preserve pair/unsure/refused/forced outcomes. Component models and forced/previous-rule sidecars are not the final answer. Interpret signed material-feature pushes, map-text evidence, range overlaps, acquisition confounding and experimental phase-split qualifications without inventing alternative profiles.
- Material feature units: siox_frac/pore_all_frac are already percentages; siox_ecd_aw is area-weighted equivalent diameter in micrometres; pore_open_excess is the all-minus-deep fraction difference; pore_chord_aniso is a dimensionless chord ratio. evidence_share is a fraction, whereas *_pct fields are already percentages. Legacy robust_z is median/IQR-scaled, not a per-class SD. The legacy validation_reference LOO_F/LOGO_F values are balanced-accuracy summaries, not per-image confidence.
- Main points explain the observed/measured characteristic, why it fits the predicted category, and why comparable alternative profiles fit less well. `cls.other_type` supplies the remaining A/B/C label. A lower probability alone is not a characteristic mismatch, and absent or incompatible alternative profiles must not be invented. Numerical and citation checks remain enabled, with full support retained in metadata.
- The explainer may return sentence lists for `headline`, `why_not_runner_up` or `agreement`. The parser joins non-empty lists of strings before the usual validator and critic checks; mixed/non-text lists remain invalid. Do not infer fusion weights from detector probabilities or confuse supplied class-evidence regions with non-class-specific attention.
- Q&A checks numeric placeholders, declared facts, exact local-source quotations and attachment IDs, retrying failed drafts. It does not run the classification grounding critic; the audit explicitly records `semantic_critic_ran=false`. The existing classification workflow retains its validator and critic.
- The reference's "verified" status describes title/abstract-level checks, not full-text verification. Its retained method guidance and illustrative ranges must not be promoted to universal thresholds or proof of sample performance.
- Fast context uses up to six relevant reference entries, omits bibliography/auxiliary fields unless requested, and filters batch records by named detector, batches and phase. It preserves verification notes, caveats, selected uncertainty fields, and the entire supplied sample. The A/B/C demo retains batch scope/limitations but does not send unmapped batch measurements. `--full-context` restores detailed selected records; compact extracts do not imply omitted data is absent.
- `main.py` defaults to three generation attempts (two left no room after a single wrong critic rejection), a 90-second HTTP-operation inactivity timeout and zero SDK transport retries. `--timeout`, `--max-attempts` and `--max-output-tokens` are configurable. Timeout is not a total-run deadline. Keep the output ceiling at 8000 by default: a live 4000-token test truncated JSON and added a retry; request brevity in the prompt instead.
- `main.py` is quiet by default: stdout carries only the result object. `--verbose` sends progress and ten-second provider-wait heartbeats to stderr; `--quiet` is accepted for old commands. The classification critic remains enabled. Parsed-draft repairs reuse the fact sheet in conversation history instead of appending it again. Audit output includes elapsed time and transport settings.

# Batch baselines (supersedes the DINO-only default)

- `main.py` and `explain_facts_document` default to `decision_mode="pipeline"`: the reported decision is explained from the record's evidence, not from the probability vector, which the website shows separately. `--dino-only` / `decision_mode="dino"` restores the DINO-only narration and still withholds every other input, including baselines.
- `sentinel/baselines.py` computes per-batch profiles (median, typical range q1-q3, n) in code from `lucas-sem-analysis-v3/outputs/batchid/*.json`, grouped by each record's `true_batch`. The language model has no knowledge of these batches; profiles must come from this data, never from the model. `--baselines DIR` selects another reference folder; `--no-baselines` disables them.
- Comparisons are like-for-like only, in two groups. *Material* measurements (pore, carbon and SiOx area, SiOx particle size, open-pore excess, pore anisotropy) come from segmentation and are compared only for v3 records (`phases.three_class_pct` + `material_model.features_S`): the legacy `examples/facts.json` comes from a different segmentation run (same image, pore 14.85 % vs 16.70 %). *Imaging* measurements are the raw-pixel `acquisition.probes` (BSE noise, dark/median/bright grey levels, InLens dark/median level, sharpness, banding, image height); all thirteen probes are byte-identical between the legacy and v3 records of the same image, so they are compared for both formats. The legacy example therefore gets `scope: imaging_only`. width_px, inlens_p99, excluded_frac and bse_file_mb are left out because they separate nothing in the reference set.
- The image being explained is left out of its own baseline (`img_` prefix normalised), so it is never compared with a profile that contains itself.
- Verdicts (`supports_reported`, `favours_<batch>`, `consistent_with_several`, `closest_to_reported_but_atypical`) are computed in code; the model narrates them and must not overturn them. The validator enforces three rules: basis/alternatives must cite the baseline; when `summary.favours_an_alternative` is non-empty at least one of those measurements must be mentioned. The whole-file critic receives the baselines so it does not judge baseline claims blind.
- When no material measurement supports the reported batch, the explanation must say so and name what the decision rests on (typically the imaging fingerprint, which may reflect the imaging session). For the demo image 71vgq3fw (High, Batch_3) none does.

# Explanations say WHY, not HOW SURE

- The website shows each image's category and probabilities separately. Explanations answer only why the image belongs to its category, using its characteristics: batch-baseline comparisons, measurements relative to the training set (robust_z, in words), where the decisive evidence lies (evidence phase shares, top regions, map_text), and imaging-fingerprint cues flagged as imaging properties.
- In every pipeline-mode sample, with or without a baseline, the validator rejects any model-score fact in the text (probabilities of any kind, push/contribution values, validation_reference, track_record, high_tier_threshold, reconstruction_error, timings_s, loo_prediction) and model-branch wording such as "DINO branch", "fused support" or "S_head". "DINOv2 evidence map" is allowed: where the evidence lies is a reason. DINO-only mode is exempt by definition.
- A facts file with N images returns an object with exactly N keys, in input order; every image gets its own left-out baseline and may not cite another image's facts.
- The whole-file critic is given the record with every model-score field removed, plus the same WHY-not-HOW-SURE rules as the writer. Given the probabilities, it rejected an honest "the measurements favour Batch_3 only weakly" as understating a 0.707 fused probability. Kind B is overstated certainty only; understatement is not a finding. DINO mode still shows its critic the scores it checks.

# The explanation is a comparison of numbers

- At least two different measurements must be compared against the baseline batches (it used to be every basis/alternatives point, which left no room for the record's own evidence): each comparison cites `measurements.<m>.this_image` and that measurement's `Batch_N.median`, `q1`, `q3`, `min`, `max` or `lower_n` (`compared_measurements`). Either half alone, or halves of two different measurements, is not a comparison. Refused and known-location answers are exempt: they explain their route.
- Imaging matches must be described as properties of how the image was acquired, never as material; with `scope: imaging_only` the limitation says only imaging could be compared.
- For the demo image 71vgq3fw the comparison shows the call's real basis: BSE noise 7.34 (Batch_3 median 8.39; Batch_1 and Batch_2 10.48) and InLens dark level 18 (Batch_3 14.5; Batch_1 0) support Batch_3, while no material measurement does.

# Whole-file critic: what may block delivery

- (In `critic_mode="blocking"` only -- see the next section for the default.) Kinds A (attention as evidence), B (overstated certainty), D (unlicensed causal story) and E (contradicts a fact) block; kind C (is a quote relevant to its sentence?) is advisory (`FACTS_CRITIC_BLOCKING_KINDS`). Quote wording is verified verbatim by code; relevance is a judgement the critic got wrong twice here (demanding a quote prove the batch; reading a baseline caveat citation as the support for the numeric comparison beside it), and one false rejection discards the whole file. Advisory objections are kept in `audit["critic_advisory_findings"]`, and `critic_passed` stays False when the critic objected.
- `CriticVerdict.passed` blocks only on a blocking-kind finding, or on a "passed: false" with no finding. It previously used `declared_pass and not blocking`, so any finding at all failed the run and `blocking_kinds` had no effect.
- When generation fails, the error lists every attempt's first reasons, not only the last attempt's.

# Speed and point form

- Effort: `ExplainerConfig.effort` defaults to `"medium"` and is sent as `output_config.effort`; `main.py --effort low|medium|high|xhigh|max|default`. Omitted, Sonnet 5.5 runs adaptive thinking at `high` before writing anything. Haiku 4.5 (the critic) takes no effort parameter.
- Caching: the first user message is two blocks, each with `cache_control: ephemeral`. Block 1 (shared knowledge) is identical for every document, so with the system prompt it forms one cache entry (~8k tokens) shared across files; block 2 is the document, re-read from cache on every repair attempt. Sonnet 5.5 caches from 512 tokens. Never put per-document text in block 1 (`test_stable_prefix_is_cached_and_identical_across_documents`). The critic is not cached: Haiku 4.5 needs 4096 tokens and its input changes every run.
- Prompt size (~40 % smaller): the baseline is shown once as a compact table with the placeholder-ID pattern stated once (`_baseline_table`), not as JSON plus a fact line per number. `_displayed_facts` hides from the displayed fact table, but keeps valid if cited: baseline facts, model scores, record values the baseline already compares, shared reference facts, and string facts (verbatim in the raw document, which is sent unchanged). DINO mode displays everything.
- Style: `STYLE_RULES` asks for dense telegraphic point form with every number, comparison, verdict and caveat kept; `;` between facts, `->` for implications, (imaging)/(material) marks, full batch names (a stray digit from "Batch_1/2" is rejected), and the shortest exact citation span. Word target 90 (repair 80); the 280-word ceiling is unchanged so a dense answer is never rejected for length.
- Whole-file critic robustness: it gets `WHOLE_FILE_CRITIC_MAX_TOKENS` (4000; it was 1200, and a few wordy objections cut the verdict off and failed the run) plus `CRITIC_BREVITY` (at most six problems, one-sentence reasons). A cut-off, malformed or failed critic call is retried once (`CRITIC_CALL_ATTEMPTS = 2`); if both fail, the run stops with the actual cause in the message, never just an exception type. Only the verdict's structure is required (`passed` bool, `problems` list); individual malformed problems are skipped by `ClaudeCritic._read`, and a rejection left with no valid finding still fails closed.

# The critic is advisory; the validator is the gate

- `explain_facts_document(critic_mode=...)` / `main.py --critic advisory|blocking|off`. Default **advisory**: the critic runs, its objections go to `audit["critic_advisory_findings"]` and `critic_passed`, and it cannot block delivery; if it fails to answer, the run still delivers and `audit["critic_error"]` says why. `blocking` restores the old gate; `off` skips the call.
- Why: across live runs it rejected correct explanations in four different ways, ending with one run whose three findings were all wrong -- a value equal to q1 called outside the typical range, a plain "below" comparison called a causal story with "atypical" misread, and required opposing evidence called a contradiction. Its objections cost retries and, in blocking mode, whole runs.
- What replaced its useful checks, deterministically in the validator: `_certainty_checks` applies the textrules certainty lists with the decision's tier (High/Medium/Low; unknown counts as Medium) -- these lists existed but were never applied to facts-file explanations; `_comparison_claim_checks` verifies "inside/within/outside <Batch_N q1> to <q3>" and "below/above <batch figure>" claims made about this image's value against the numbers, with inclusive ranges, ignoring equal displays and comparisons in a different clause. Attention-as-evidence (kind A) has no target: no record contains an attention map.
- Mutation tests must run on a scratch copy of the project, never by editing these files in place: an open editor buffer saved a mutated `pipeline_facts.py` and an older `tests/test_speed.py` back over restored files.

# More than medians

- Per batch and measurement the baseline gives median, typical range (q1-q3), observed range (min-max), n, and `lower_n` (how many of that batch's images are lower than this image -- its rank), plus `typical_ranges_separate` (batch pairs whose typical ranges do not overlap). `_baseline_table` renders a block per measurement.
- Breadth rule (`_evidence_breadth_checks`): an explanation must draw on at least `MIN_EVIDENCE_KINDS` (3) of the kinds the record offers: batch baseline, composition (`phases`, `phase_fractions_pct`, `material_range_rule`), measured features (`features_S` value/robust_z, `fingerprint_model.top_measurements`, `texture_model.top_features`), and where the top evidence lies (`evidence.*`, `material_model.map_text.*`). A kind counts as available only if the record has a displayed numeric fact of it; the baseline is counted explicitly because its facts appear in the compact table, not the fact table (missing this rejected every baseline + two-kind answer). Refused and known-location answers are exempt.
- Claim checks also cover "inside/outside <min> to <max>" (observed range) and "lower/higher than all <n>" (must match `lower_n` = 0 / = n). "below/above" is checked only against values (median, q1, q3, min, max), never against a count.
- "decisive" is a certainty word below High confidence, but "decisive area/region(s)" names where the evidence lies: `_AREA_WORDING` exempts it, and the prompt says "top-evidence area" (the field is `phase_share_in_top10pct_evidence_pct`). The earlier prompt example "Decisive area: ..." taught the model a word its own validator rejected.
- Superseded by "Short points" below for word targets.

# Short points

- One idea per point, at most `MAX_POINT_WORDS` (22) words counted after placeholders are filled in; the validator (`_point_length_checks`) rejects past `HARD_POINT_WORDS` (26) so a slight slip does not cost a retry. Up to `MAX_POINTS` (7) points, so data moves into more short points instead of being chained with ";". Word target 110 (repair 95), ceiling 280. The manifest's word_budget carries `max_words_per_point`.
- The model copies the length of the prompt's example sentences: a 35-word example produced 35-word points. `tests/test_point_length.py::test_the_prompt_examples_are_themselves_short` keeps every example in BASELINE_RULES and RECORD_EVIDENCE_RULES within 22 words.
- Displayed units are short: "pp", not "percentage points".

# Pitch latency and checked-response caching

- `main.py` keeps Sonnet as the default but now uses `--effort low`; `--effort medium` restores the previous setting. `--model` is an explicit override, not a guarantee of lower latency. Haiku trials incurred formatting repairs, so there is no automatic smaller-model switch. Haiku requests omit the unsupported effort parameter.
- Facts-file CLI requests use `short_ids=True`: short `{fN}` transport aliases expand to the original owned fact IDs before validation and critic review. The model omits the redundant `facts` list; code derives it from the actual text placeholders. Unknown facts, cross-sample references, unsupported numbers, baseline comparisons, evidence breadth and point-length checks remain active. Library callers can opt in with `short_ids=True`; the canonical response contract stays unchanged.
- The facts CLI caches completed AI responses in `explanations/.cache` (already gitignored), with a 24-hour TTL. Library callers opt in using `cache_dir`. `--no-cache` bypasses reading and writing; `--refresh-cache` forces fresh generation and writes only after successful checks; `--cache-dir` selects another local directory. Entries are private atomic JSON files, not pickle; malformed, expired or checksum-invalid entries are misses.
- Cache identity includes the original document hash (also in DINO mode), full request, model/effort and critic configuration, knowledge version, computed baselines, fact values/displays and the implementation fingerprint. All sample explanations are cached together. Input files are never rewritten. The cached canonical draft is revalidated against the current context before rendering; rejected/incomplete generation and unavailable critic runs are not cached. An advisory critic objection remains advisory and remains recorded when reused.
- Cache hits reuse the original critic verdict, not a new critic call. The audit exposes `cache_hit`, `cached_critic_verdict`, `semantic_critic_ran_this_run`, original timings and zero current generation/critic time. A valid hit needs no API credential or network request. `--verbose` identifies cache reuse; stdout remains the existing sample-ID-to-bullet-string JSON object.
- Before a demo, run the exact command once with the intended facts, model and critic settings. Identical subsequent runs reuse that checked response; new inputs, settings, references or code require generation. Caching does not make unseen-image inference instantaneous. Tests isolate CLI caches in `tmp_path` so scripted answers cannot populate the demo cache.
